### Audit findings — Aug 3 (Date Night feature audit + fix sprint)
- ✅ Full audit of Date Night end to end — every API route, the custom-date create/edit/detail pages, the suggestion engine, and the hero-photo/reaction helpers. Distinct from every other feature audited this engagement: custom-date create/edit/detail don't go through API routes at all — they write directly from the browser to Supabase, so authorization there lives entirely in Postgres RLS policies rather than `requireUser`/`verifyCoupleMembership`. Verified the actual policy SQL (not just policy names) with Matt via the Supabase SQL Editor before concluding anything — `pg_policies` showed SELECT/UPDATE both correctly scope to couple membership via an EXISTS against `couples`; INSERT was the one real gap.
- ✅ CRITICAL, applied by Matt Aug 4 — `docs/database/custom-dates-insert-policy-fix.sql`: the `custom_dates` INSERT policy only checked `auth.uid() = user_id`, never that `couple_id` actually belongs to the caller (unlike SELECT/UPDATE, which both do). An attacker could insert a row with their own user_id but a stranger couple's couple_id — SELECT/UPDATE's couple-scoping would then make the planted row visible (and editable) to the real couple, but the delete flow (keyed on the row's own user_id/shared_with fields, not couple_id) means the victims couldn't remove it themselves. Fix adds the same couple-membership EXISTS check to INSERT's WITH CHECK that SELECT/UPDATE already have, while still allowing couple_id IS NULL. Run in the Supabase SQL Editor and verified live via `pg_policies` — the INSERT row's `with_check` now shows the EXISTS clause.
- ✅ Confused-deputy fix, commit 098df46: `dates/conversation-starters` verified the caller belongs to the supplied `coupleId` but then updated `custom_dates` by a separately-supplied `dateId` with no check that the date actually belonged to that couple — same bug shape already fixed twice this engagement (`follow-through/report`, `ritual/update`). Added `.eq('couple_id', coupleId)` to the update.
- ✅ Cost-abuse fix, commit 098df46: `dates/suggestions` (GET+POST) was the one Date Night route with zero auth at all, unlike its sibling `ticketmaster` route which requires a session for the same class of external-API proxy — left open, anyone (logged in or not) could hammer the Google Places API key through it for free. Added `requireUser`. POST also had an unused service-role Supabase client, created but never referenced; removed. Client callers (`fetchDateSuggestions`/`fetchNearbyPlaces` in `lib/date-suggestions.js`) sent no Authorization header at all before this — updated both, otherwise this fix would have silently broken "Ideas For You Two" entirely.
- ✅ `getHeroPhoto()` fixed, commit 02f1960 (`lib/date-night.js`): two bugs. (1) Docstring claimed it prefers real-location photos over custom/manual stops; the code actually concatenated locationPhotos + otherPhotos into one array and picked proportionally — 1 location photo + 3 custom-stop photos meant a 75% chance the hero was a custom stop, the opposite of the stated intent. Now picks only from locationPhotos when any exist. (2) Media stops (movies/shows) were miscategorized as location photos — the old check only excluded `custom-` prefixed place_ids, not `media-` ones. Both fixed.
- ✅ Dead code cleanup, commit 02f1960 (`lib/date-suggestions.js`): removed an unused `weakAreas` variable and an unreachable fallback branch (`Object.keys(DATE_CATEGORIES)` always has entries, so the "no assessment data" fallback could never trigger). The creator could request deletion and then only ever cancel it back, never complete it. Fixed by having `/delete/request` delete immediately when the date was never shared, skipping the two-party flow entirely (a solo date doesn't need a partner's sign-off to remove). Updated both client callers (`app/dates/[id]/page.js`, `app/dates/[id]/edit/page.js`) to handle the new immediate-delete response.

Also aligned `custom_dates`/`date_plans` query ordering (was `created_at` vs `date_time`, inconsistent though masked by a client-side re-sort) and added the `date_plans` status exclusion (`cancelled`) that `custom_dates` already had (`pending_delete`) — a cancelled date_plans row would previously still show up in history.
